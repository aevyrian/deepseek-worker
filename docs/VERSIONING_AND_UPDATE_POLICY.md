# 版本号与自动更新发布规范

> 适用于 DeepSeek Worker Connector 的后续修改、修复、打包、GitHub 发布与个人试用升级。所有开发/修复/发布 Agent 必须遵守；与具体版本号无关，长期生效。

## 一、三段式版本号

采用 `主版本号.次版本号.修订号`（MAJOR.MINOR.PATCH），例如 `0.7.13`：

| 修改级别 | 递增部分 | 例子 | 适用范围 |
| --- | --- | --- | --- |
| 小修复 / 小调整 | 最后一段 PATCH +1 | `0.7.13 → 0.7.14` | 普通 Bug、可靠性、兼容性和局部细节修复 |
| 项目功能 / 阶段性升级 | 中间一段 MINOR +1，PATCH 归零 | `0.7.13 → 0.8.0` | 新功能、较明显的模块或工作流能力变化 |
| 首个正式稳定版 / 后续重大不兼容升级 | 最前一段 MAJOR +1，后两段归零 | `0.9.x → 1.0.0`；之后 `1.x.y → 2.0.0` | 完成正式发布验收后的首个 1.0.0，以及后续重大不兼容版本 |

- 尚未达到正式发布门槛时保持在 `0.x.y` 系列；**仅改变版本号不能证明稳定性**。尤其当前 P0 自动回传若缺真实 A/B 会话、Project Event ACK 闭环验收，应明确标识试用/预发布而非稳定版。
- 仅在需要对用户**分发新构建**时递增版本；未分发的中间开发提交和仅更新文档不要求每个 commit 都升级版本号。
- 已经公开发布的版本号、Git tag 和 Release 不可重新指向不同代码；如需修复，递增新版本。

## 二、唯一受支持的更新渠道（强制）

**正确渠道：** 修改并核对版本声明 → 生成经过测试的固定 Git commit → 推送受信任的官方仓库 `aevyrian/deepseek-worker` → 创建匹配的 `vX.Y.Z` Git tag（及相应 GitHub Release / 预发布标记）→ 使用 Connector 原有的“检查更新 / 一键更新”或 Harness 官方 Desktop Plugin Manager 安装 → 按提示重启 Harness → 核验运行 Build Hash。

**错误渠道（禁止）：** 不发布对应版本/tag、只修改本地源码或安装目录就把它当成“已更新”；用一般 CLI 绕过 Desktop Plugin Manager 受控 profile；手动复制、覆盖 Connector 插件文件；使用未知/非官方 GitHub 安装来源；仅凭 UI 的版本号推定实际运行的代码已切换。

曾经实际观察到：**先按正确流程发布版本号，现有自动更新可以工作；直接改文件或用非受支持渠道更新会报错。** 因而今后的常规小修、小功能更新，优先走正常发版及内置更新流程，不再把“手动替换源码”作为升级方式。

## 三、执行顺序与验收门槛

1. 检查当前远端版本、Git tag、Release、安装来源、默认分支和本地未提交改动。防止重复版本、重用 tag、覆盖其他人的工作。
2. 在独立分支/工作树完成修改，按第一节规则决定下一版本；同步需要变更的 package/更新元数据和 `CHANGELOG.md`。保证所有公开显示及安装所依赖的版本一致。
3. 按改动范围执行定向与全量测试、必要语法检查、差异检查和打包核对。记录完整 Git SHA、包指纹与测试结果。**仅单元/模拟测试通过不等同于真实 ChatGPT 多聊天回传验收。**
4. 将**精确**提交推送官方 GitHub；创建 `vX.Y.Z` tag 并核对其指向；生成对应 Release。未通过真实 E2E 的版本必须在 GitHub Release 标为 **Pre-release**，并明示仍未验收的能力、回滚方式；禁止伪称 stable。
5. 升级前保留现有安装、配置、Outbox、必要回滚备份；遵守 Worker Drain/空闲检查。通过内置自动更新或受支持的官方 Harness Desktop Plugin Manager 安装；如需重启，重启后再次核验**实际加载的 Build Hash**，不能只检查磁盘或 package 版本。
6. 真实验证时区分 `Task Completed`、`Delivery ACK` 和 `Project Event ACK`；没有 ChatGPT 真实接管、读结果及正确事件 ACK 的证据，不得宣称自动闭环成功。

## 四、对开发 Agent 的明确约束

- **不要因修复“只有几行代码”就绕过发版渠道。** 需要用户收到更新时，仍应递增正确版本段，并产生可追溯的新 tag / Release；开发测试可在独立分支进行，但不得直接覆盖运行中的桌面插件。
- 如果发现来源不可信、候选 SHA 与构建不一致、生产 Worker 有任务、现有 Outbox 状态不明、GitHub tag 冲突或官方安装管理入口不可用，应停止部署并报告阻塞，不能强行覆盖、清空历史或猜测成功。
- GitHub Release 的 **Pre-release** 标志不等同于另一个正式稳定版本，也不替代 `0.x.y` 的版本递增规则。除非已证实更新器支持先行版本字符串，否则不要擅自引入与更新器不兼容的后缀。
- 未获明确授权，不因版本升级改动生产 Site/D1、删除消息、ACK 既有 Project Event、重置 Outbox、强推 `main` 或重写既有 Git tag。
